## Дорожня карта `subit-civ`

### Фаза 0 — Завершення MVP (v0.1.0)

**Що вже є:**
- Структура репозиторію
- `README.md`, вимоги, конфігурація, `.gitignore`
- База даних: схема, seed-дані, скрипт `build_db.py`
- Заготовки модулів `src/__init__.py`, `src/db.py`
- Ноутбук `simulation.ipynb` з кодом для завантаження даних і візуалізації

**Що потрібно дописати, щоб симуляція запрацювала:**

1. **`src/rules.py`** — реалізувати чотири функції правил `apply_rule_1`…`apply_rule_4`, а також функції `meta_evolution` (перемикання правил за порогами) та `classify_omega` (визначення Ω-класу). Логіка вже обговорена: рівняння з параметрами з YAML, перевірка порогів.

2. **`src/evolution.py`** — функція `run_simulation(params, stress_func)`, яка створює початковий стан, у циклі на кожному кроці викликає `meta_evolution`, потім відповідне правило, оновлює стан і додає його до траєкторії.

3. **`src/db.py`** (доповнити) — зараз там лише функція підключення. Можна додати функцію для збереження результатів симуляції в таблиці `simulation_runs` та `trajectories`, щоб ноутбук міг не лише читати, а й писати в БД.

Після цього ноутбук `simulation.ipynb` можна буде запустити повністю, і він покаже графіки P, M, E, Ω, а також порівняє симуляцію з археологічними оцінками населення.

**Результат Фази 0:** працюючий прототип, який можна демонструвати, тестувати й доповнювати даними.

### Фаза 1 — Валідація та повноцінна БД (v0.2.0)

1. **Розширити схему БД** до багатошарової архітектури:
   - Таблиці для артефактів, біологічних решток, радіовуглецевих дат, кліматичних проксі.
   - Універсальна таблиця `observations` (як у вас уже є) + окремі представлення для population, monuments, trade тощо (або залишити універсальною з `type`).

2. **Наповнити даними** з реальних публікацій: Shady 1997–2025, Haas & Creamer 2006, Sandweiss 2009, Coutts 2011 тощо. Додати більше seed-файлів (артефакти, клімат, джерела).

3. **Модуль валідації** (`src/validation.py`):
   - Завантажувати з БД спостереження та порівнювати їх із результатами симуляції на відповідних кроках.
   - Обчислювати, чи потрапляє симуляція в довірчий інтервал спостережень.
   - Зберігати результати в таблицю `validation_comparisons`.

4. **Додати ноутбук `03_validation.ipynb`**, який візуалізує відповідність моделі даним.

### Фаза 2 — Provenance та експерименти (v0.3.0)

1. **Таблиці джерел та цитувань** (L0, L−1): `sources`, `citations`, `datasets`, `extractions`.

2. **Реєстр експериментів** (`simulation.experiments`, `experiment_hypotheses`):
   - Створити два експерименти (Формування та Занепад) з формальним описом, гіпотезами, тестами.
   - Додати таблицю `distinguishing_tests` і `test_results`.

3. **Симуляція з варіаціями**:
   - Можливість запускати кілька прогонів з різними параметрами (наприклад, різні дати кліматичного стресу).
   - Ноутбук `04_experiments.ipynb` для порівняння гіпотез.

4. **Початок ведення `provenance`**: кожен run прив’язується до версії БД, гіт-коміту, набору правил.

### Фаза 3 — Логічний шар L6 (v1.0.0)

1. **Таблиця `logic.assertions`**:
   - Типи тверджень: `axiom`, `definition`, `derived_fact`, `hypothesis`, `theorem`.
   - Статуси істинності: `supported_by_data`, `formally_proved`, `conjecture`, `falsified`.
   - Поля `derived_from` (посилання на сутності) і `proof` (коротке обґрунтування).

2. **Скрипт для автоматичної генерації тверджень** з результатів валідації:
   - Якщо симуляція потрапляє в ДІ для населення в SUMMER — генерується твердження «Караль був метастабільним монументальним суспільством».
   - Якщо тест на безперервність культури (Vichama/Peñico) позитивний — твердження про керовану міграцію.

3. **Ноутбук `05_logical_assertions.ipynb`** для перегляду та експорту логічного корпусу.

## Що робити прямо зараз

1. **Написати `src/rules.py` та `src/evolution.py`** з використанням параметрів із YAML.
2. **Протестувати симуляцію локально** — запустити ноутбук, переконатися, що графіки генеруються.
3. **Зафіксувати перший реліз**:
   ```bash
   git add .
   git commit -m "Working Caral-Supe simulation MVP"
   git tag v0.1.0
   ```
